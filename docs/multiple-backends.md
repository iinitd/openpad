# Multiple backend connections

Puff can retain several Paseo direct, Paseo relay, OpenClaw, and OpenCode connections at once. Open **Settings → Add connection** to add another server. The current connection stays online while the new connection is established, and a failed addition leaves the current writing view available.

Settings and the connection page list live and saved connections. **Switch/Open** changes the active writing context. **Disconnect** closes only that connection; another connected backend becomes active if available. A disconnected profile remains available for **Retry**, and an explicitly disconnected profile does not reconnect on launch. Successfully connected profiles otherwise reconnect independently at startup.

The left sidebar's **Projects** tab displays two levels: connection source, then projects grouped by working directory (`cwd`). Multiple backend workspace IDs or sessions sharing the same directory produce one project row; pinned projects appear first. Selecting a project restores its most recently used available session, falling back to its latest session. Individual sessions stay in the Agent sidebar's session picker, which lists only unarchived sessions in the current project: the active connection and the same normalized working directory (`cwd`). Sessions with different backend workspace IDs still appear together when their cwd matches. Selecting another project updates the session list; an identical path on another backend belongs to a separate project. Switching sessions within the same connection and cwd keeps the project catalog, file tree and current preview in place, even if the sessions have different native workspace IDs. It does not trigger a project loading banner or restart catalog discovery. This directory grouping is a Puff navigation concept; native backend workspace and project identities remain unchanged. Projects and sessions open directly in the writer. A shared host flow restores remembered sessions before discovery, and automatically chooses a provider when a project needs its first session. The writer shows loading or retryable errors during opening; there is no separate New Writing Session page. Puff qualifies list keys by connection identity, so two servers can use the same path or session ID without sharing state. Opening a listed session activates its source connection before fetching its metadata/history. Each source reports its own discovery errors.

The editor displays one session at a time. Switching its connection resets the foreground view and restores the destination's preferences, files, and history. It does not cancel work running on the previous backend. Permission handling retains Puff's existing allow-once behavior for inactive connections. Follow-up messages still waiting in Puff's local queue stay saved with their originating backend/session and resume when that session is restored; they are not dispatched to the newly active backend.

Click a connection source header in **Projects** to collapse or expand its project list. Each source remembers its state across sidebar remounts and app restarts. Collapsing a source does not disconnect it or change the selected session.

Each expanded source also offers **Add project**. It opens a folder browser rooted at the active session's directory (or that source's first known project), lists only subdirectories, and lets the user walk into them. The up control (or the **…** row) goes back one level; at the starting root it re-roots the browser at the parent directory, so sibling and higher folders are reachable. Choosing a folder opens it as a project and creates its first session when needed; the catalog is refreshed afterward. Walking above the starting directory depends on the backend's directory-read scope; failures keep the current folder and show an error. The action is disabled while its connection is offline.

Model choices, recent sessions, pinned workspaces, document positions, previews and queued inputs are scoped to the connection endpoint. Background request completion updates its originating context. Content plugins receive only workspace-bound file capabilities and host open actions; they do not manage connections.

Verification covers connection addition/failure isolation, independent disconnect and retry, concurrent attempts, saved-profile restoration/migration, stale callbacks, source-qualified catalogs, endpoint queues and pins. Real simultaneous server connections and native interactions still need verification in the selected deployments.

OpenCode connections follow the same source-qualified rules. Provider choices map to OpenCode agent profiles, and sessions map to OpenCode sessions; OpenCode project directories fill the Projects tab. See [Connecting to an OpenCode server](opencode-connection.md) for setup, CORS, and protocol requirements.

Backend development is OpenCode-first. New capabilities are implemented and verified against OpenCode; the Paseo and OpenClaw adapters are maintained as-is and are not changed as part of ordinary feature work. Capability gaps in those two backends are documented or degraded in the UI rather than emulated. This policy is also recorded in the project `AGENTS.md` and `README.md`.
